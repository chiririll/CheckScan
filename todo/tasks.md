# CheckScan — саммари и задачи

Модель данных: [model.md](model.md). Сценарии: [usecases.md](usecases.md). Экраны: [screens.md](screens.md). Задачи ниже без модели не начинать.

## Цели

CheckScan — не второй Savvy. Сюда падают **чеки** (QR, ручной ввод, потом рынок). Savvy считает **конверты жизни**. Пересечение есть, но вопрос разный.

| Цель | Это CheckScan? | Это Savvy? |
| --- | --- | --- |
| История покупок: что, где, когда, за сколько | Да, ядро | Нет, ему всё равно какой SKU |
| Где дешевле и как цена едет | Да, ядро | Нет |
| Сколько ушло на то, без чего можно было обойтись | Да, но прицельно: теги и конкретные товары, не «еда за месяц» | Да, но грубо: конверт «продукты / кафе» |
| Список покупок | Вкладка у кассы: темп + фасовка + где дешевле. Пока ядро врёт — экран пустой, слот уже есть | Нет |

Грань проходит по **двум уровням категории**, их сейчас нет: список плоский (`#dairyEggs`, `#grocery`, `#home` рядом).

- **Верх** (Продукты, Для дома, Кафе, Транспорт, Аптека) — конверт Savvy. Транзакции и синхронизация живут только здесь.
- **Низ** (Бакалея, Молоко, Бытовая химия, Снеки) — аналитика CheckScan: «можно было обойтись», структура трат внутри продуктов.

CheckScan отвечает «что купил и стоило ли» (низ + товар + цена). Savvy отвечает «сколько осталось на жизнь» (верх). Не дублировать в CheckScan конверты и «остаток до зарплаты». Позиции в транзакции Savvy — необязательная справка, не единица учёта.

Список — вкладка бара ([screens.md](screens.md)), не аналитика и не «потом решим, есть ли он». Пока нет честных `unitSize` и товара экран пустой (3.1). Если без списка у кассы жить можно — не спешить наполнять, слот не убираем.

## Что доработали

- Категории: два уровня. Верх = Savvy, низ = аналитика здесь. Сейчас список плоский.
- Товар: не паспорт характеристик. Теги на товаре и на кассовом названии; класса нет. Молоко и мармелад — один товар; билет — услуга, руками.
- Сети магазинов → продавец + политика чека (разбирать SKU / повесить всё на верх). Рынок = ручной чек, не новый документ. Кафе не засоряет каталог.
- Бюджет в CheckScan → «траты зря» на Главной (низ + теги товара). Конверты и лимит на жизнь — Savvy. Список — вкладка у кассы, наполняется из темпа.
- Экспорт в Savvy: только верх, сплит если в чеке разные верхи. Позиции в транзакции — справка, не учёт.
- Поиск на карточке товара и потолок кластера — раньше аналитики. Почта, акции, срок, рецепты — не сейчас.

## Итерации

Три поставки. Внутри — старые номера (0.x–3.x), чтобы не плодить вторую нумерацию.

| # | Зачем | Что внутри | Готово когда |
| --- | --- | --- | --- |
| 1 | Собрать товар и продавца | гигиена 0.1–0.3, схема, 1.0–1.4 | Чек разбирается: два уровня, теги, поиск на товаре, ассист с потолком, магазин с parse/ignore. Список на баре пустой. Главная ещё старая. |
| 2 | Главная как в [screens.md](screens.md) | `purchase`, 2.1–2.3 | Блоки Цены / Траты зря / Чаще всего / Магазины считают с лежащих чеков. ₽/ед честная. |
| 3 | У кассы и в Savvy | 3.1–3.3 | Список наполнен из темпа. Ручной чек со Скана. Экспорт верха в Настройках. |

Итерацию 2 не начинать, пока в 1 нет сети и товара, на который вешаются названия. Иначе блоки соврут.

Почта, акции, срок, рецепты — ни в одну итерацию.

## Итерация 1 — каталог

Сначала гигиена (не зависит от модели), сразу схема из [model.md](model.md): integer PK, `item` вместо `positions`, `merchant`, `purchase` пустой, `check.merchant_id`. Без этого 1.0–1.4 снова лягут на uuid.

### 0. Гигиена

Снять с дороги до или вместе со схемой.

#### 0.1 Декомпозиция `database.dart` на миграции

Сейчас схема и апгрейды живут в одном файле: `checkScanDbVersion = 5`, `onCreate` / `onUpgrade` с лестницей `if (oldVersion < N)`, плюс `create*` и `migrate*` рядом.

- Вынести каждую версию в отдельный шаг (номер + `up`).
- `onCreate` прогоняет все шаги с нуля.
- `onUpgrade` прогоняет шаги `(oldVersion, newVersion]`.
- Сидер категорий остаётся шагом или явным хуком после создания каталога, не размазанным по `if`.

#### 0.2 Pull-to-refresh на чеке

На [receipt_page.dart](lib/features/receipt_detail/receipt_page.dart) «Обновить данные» сидит в `PopupMenuButton` рядом с крошками «История › Чек».

- Обновление одного чека — тянущий жест вниз по телу страницы (`RefreshIndicator` на существующий `refreshReceipt`).
- Индикатор занятости не должен дублироваться бессмысленно (сейчас ещё и `LinearProgressIndicator`).
- Удаление чека остаётся в меню. Пункт refresh из меню убрать.

История («Догрузить состав» пачкой) — отдельно, не смешивать с этим жестом.

#### 0.3 Крошки каталога: одна кнопка → попап

[CatalogTrail](lib/features/catalog/catalog_trail.dart) рисует всю цепочку в одну строку. На категории и товаре это «Каталог › Категории › Молочка › Молоко» плюс кнопки; на узком экране это меню, а не навигация.

- Текущий пункт — заголовок.
- Один контрол открывает попап/меню с предками и переходом назад по цепочке.
- Тот же виджет на категории, товаре, черновике и ассисте, не отдельная реализация «только в категориях».
- Действия (удалить товар, копировать/вставить ассист) не живут внутри крошек.

### Каталог

Без этого итерация 2 врёт.

#### 1.0 Два уровня категорий

Сейчас `categories` без родителя, сиды — плоский список. Нужно ровно два уровня, не дерево произвольной глубины.

- Верх: Продукты, Для дома, Кафе, Транспорт, Аптека, … — ключ синхронизации с Savvy.
- Низ: Бакалея, Молоко, Бытовая химия, … — висит на верхе. Товар крепится к низу (или к верху, если детей нет: кафе).
- Чек с политикой `ignore` получает верх целиком (Кафе), без листьев в каталоге.
- Один чек Магнита может дать сплит в Savvy: Продукты + Для дома, если в нём листья разных верхов. Внутри CheckScan сплит не нужен — там видны листья.
- Текущие сиды разложить: молочка/мясо/бакалея/снеки → под Продукты; `#home` сегодня один бакет, его нельзя просто объявить родителем без миграции.
- Экспорт и UI выбора «категория транзакции» не показывают низ.

Это и есть граница функционала: низ не уезжает в Savvy, верх не обрастает аналитикой цен.

#### 1.1 Теги

Свободные метки на товаре и на item. Один словарь `tag`, связи `product_tag` / `item_tag`. Класса нет: «премиум» — тег, если нужен.

- Человек ставит сам. Отдельного экрана «теги» нет: с карточки товара ([screens.md](screens.md)).
- «Траты зря» (2.3) режет по низу и по тегам **товара**. Теги item в этот блок не кладём: `purchase` схлопывает пачки.
- Словарь и связи — здесь, в 1.1. Сам разрез на Главной — после того, как товары собраны.

Молоко: один товар, цены в ₽/л. Снеки/мармелад: один товар. Билет: не автосклейка, товар-услуга и ручные алиасы.

#### 1.2 Карточка товара: поиск и кандидаты

Из `features.md`, делать раньше любой новой аналитики.

- Поиск по неназначенным (и по уже чужим?) item, чтобы повесить на этот товар.
- Блок «похожие» — кандидаты из кластера, не автоприменение.
- Снять item с товара без удаления самой карточки.

#### 1.3 Ассист не должен сходить с ума

- Жёсткий потолок размера кластера. 110 строк в один товар — баг.
- Не склеивать, если совпал только бренд, а следующий токен разный.
- Не склеивать услуги (проезд, билет) с едой. Без словаря брендов склейку по бренду до нуля не довести — и не надо.

#### 1.4 Магазин как сущность

Не конструктор иерархий, а нормализация продавца.

- Алиасы `merchant_name` → merchant; сеть — `merchant.parent_id`, не отдельная таблица.
- Политика и верх категории на merchant:
  - **parse** (продукты, рынок) — строки в item, цены, «где дешевле»;
  - **ignore** (кафе, ресторан; опционально транспорт) — чек целиком на верх, строки не в каталог.
- Политику можно включить на конкретном магазине, не только на типе.
- Сравнение цен группировать по сети, не по сырой строке чека.
- UI: блок «Магазины» на Главной → список продавцов → Магазин ([screens.md](screens.md)).

## Итерация 2 — Главная

Имеет смысл, когда товары хоть как-то собраны и суммы в основном привязаны к категории. Кэш `purchase` пересчитывать в одном месте. Бар: слот Списка по-прежнему пустой.

#### 2.1 Цена за единицу

Блок «Цены» на Главной и карточка товара: ₽/кг, ₽/л, ₽/шт из `unitSize` + единицы товара. Без этого сравнение пачек 300 г и 1.75 л бессмысленно.

Эталон пачки, если у молока их несколько — большая / последняя, не среднее из `purchase` ([model.md](model.md)). Сейчас виджет на главной берёт сырую `unitPrice` самой частой позиции и имя магазина как есть.

#### 2.2 Динамика и магазины

- График/список цены товара во времени (экран «Цены» с Главной → Товар).
- Разрез по сети (после 1.4).
- «Чаще всего» — темп; оттуда потом строки в Список.
- Это запрос к существующим чекам, не новая доменка.

#### 2.3 «Траты зря»

Блок Главной ([screens.md](screens.md)): тизер — сумма за период; экран — низ и теги товара. Не конверт Savvy.

- Сумма за период по **низу** и по тегам товара (`purchase`). Верх здесь не режет.
- Теги item не участвуют: в чеке пачки одного товара схлопнуты.
- Чеки с `ignore` не дробятся: кафе — одна сумма на верхе, в этот блок не режем как «зря».
- Месячный лимит на «все продукты» не нужен. Конверты жизни — Savvy.

## Итерация 3 — список, рынок, Savvy

После того как контур «товар → цена» честный на реальных чеках.

#### 3.1 Список покупок по темпу трат

Вкладка уже на баре. Наполнение — после 2.1/2.2: расход / фасовка → «возьми 2 упаковки», плюс «в этом магазине дешевле». Строки приходят с «Чаще всего». Без честных `unitSize` и товара экран пустой, не мусор. Не отдельный продукт.

#### 3.2 Ручной чек (и рынок)

Вход уже на Скане: «без QR» ([screens.md](screens.md)). Позже плюс в Истории. Форма без OCR: магазин, дата, строки из известных товаров (автокомплит), цена и количество. OCR/голос — на ту же форму позже.

Рынок — зачем форма нужна: нет QR, те же товары, что в магазине. Смысл — где дешевле (рядовка vs Макси), не новый тип документа. Merchant с `parse`. Полную форму имеет смысл после каталога и цен, иначе сравнивать не с чем.

#### 3.3 Экспорт и синхронизация с Savvy

Пункт в Настройках ([screens.md](screens.md)), не блок Главной. Транзакции получают **только верх**. Низ, товар и цена остаются здесь.

- Один чек → одна транзакция, если все листья одного верха.
- Иначе сплит по верхам (продукты + для дома), не по молоку и бакалее.
- Кафе / политика «игнорировать» → одна сумма на верхе, без строк.
- Позиции в транзакции Savvy — необязательная справка человеческими товарами, не сырой чек и не ключ синхронизации.
- Имеет смысл после 1.0 и политики магазина. Иначе в Savvy уедет плоский список сидов.

### Позже / не делать сейчас

| Идея | Почему не сейчас |
| --- | --- |
| Импорт чеков с почты | Отдельный коннектор, хрупкие провайдеры. Нужен, когда ручной ввод есть и не хватает полноты. |
| Акции с сайтов магазинов | Чужой HTML, ToS, не local-first. Смотреть на уже заплаченную цену. |
| Срок годности | В чеке его нет. Ручной ввод не будут заполнять; штрихкод + внешняя база — другой продукт. Пометка в `features.md` («нормальный срок + частота») это не чинит. |
| Рецепты из недавних покупок | База блюд и инвентарь. К кассе и бюджету почти не клеится. |

UI целиком сюда не тащим. Исключения — только то, без чего каталог и чек нельзя нормально собрать: крошки, pull-to-refresh, карточка товара.
